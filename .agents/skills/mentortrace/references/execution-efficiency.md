# Execution efficiency

After formal verification freeze, use the guarded unchanged-claim comparison in
[review workflow](review-workflow.md). Do not repeatedly rediscover a diagnosis
whose complete claim, conditions and uncertainty are explicitly preserved. Keep
its original provenance; new facts and changed claims still need evidence.
This reuse can inherit an earlier diagnostic error and is not fresh verification.

These rules apply to the distributed MentorTrace workflow, not a user's global Codex configuration. They optimize repeated processing while preserving required evidence, coverage, independent contexts and both delivery gates. No reduction in reasoning effort is authorized by this document. Frozen runs and original responses stay immutable.

## Reuse valid completed stages

Before submitting, compare the actual prompt hash, ordered page-image hashes, applicable stage rules and actual model/effort. Reuse a complete matching response with its original provenance and a verified output hash. Do not relabel an older response as newly generated by different settings. Changed postprocessing instructions need not invalidate unchanged initial requests; changes to manuscript or initial-lane rules require the relevant fresh review. Provider input caching is not response reuse and does not remove a generation call. A completed but unreadable/unknown judgment remains unknown.

`run_authorized_stage.py` reuses matching completed attempts in the current stage directory. Conflicting or modified cache records require inspection, not an automatic paid rerun. Legacy records without an output hash require explicit reconciliation; never manufacture provenance to make them reusable.

## Renew only affected delivery reviews

Bind original requirements, final fields, report blocks, drafts, evidence and use conditions. Determine the change scope, including English/Chinese counterparts, local prerequisites, shared plans and cross-section uses. Changes to context or evidence can invalidate unchanged text. Reuse frozen A only when its bound original requirements and manuscript evidence remain valid. Compare B to the current final fields and report; a report hash update is not a substantive review.

Use `scripts/prepare_delivery_delta.py` to prepare a fresh version-2 ledger and a pending-record plan from a previously validated report/ledger. It checks exact inventories, complete local contexts and evidence hashes. Carryover additionally requires a recorded reviewer assessment of affected source/target IDs and cross-context links. Without that assessment it lists reuse candidates but leaves judgments pending. Changed global meaning or an incomplete dependency assessment requires broader renewal. The fresh global scope/completeness declarations and report-bound B gate still need actual review. Preserve prior reviewer identities and exposure. This helper never invokes a model or certifies semantics.

```text
python scripts/prepare_delivery_delta.py --previous-ledger OLD/delivery.json --previous-report OLD/report.md --report NEW/report.md --out NEW/delta-plan
```

Inspect `pending.json` and complete a copy of `assessment.template.json`: its bound hashes, `reviewer`, `reason`, `cross_context_review`, `affected_source_ids`, `affected_target_ids` document the actual change/dependency assessment. Do not claim independence for an editor's scope judgment. Then run the same command with `--assessment NEW/assessment.json --out NEW/delta-reviewed` to carry eligible records and list remaining work. The helper conservatively invalidates whole local contexts, keeps stable IDs, and declines reuse if old records no longer validate; it does not infer equivalence or remap shifted IDs. Use original provenance for inherited records and truthful provenance for the new scope assessment.

## Delivery task reuse and lossless records

New adaptive protocols pin `postprocess_efficiency: 1`. `prepare-delivery` consumes the
ledger produced by `prepare_delivery_delta.py` with an actual affected-scope assessment.
It independently recomputes reuse eligibility and compares every claimed carried record.
Only unchanged source fields, target units and Expression groups with valid prior review,
full local context, evidence hashes, cross-context assessment and identical applicable
delivery rules/settings may be omitted from fresh task assignment. Earlier ledgers without
the rule binding receive complete review; manually populated pass fields do not authorize
reuse. A changed dependency invalidates its records even when their text is unchanged.

The new reviewer receives the complete current report, source inventories, manuscript
and carried judgments with their provenance. Coverage/B, global completeness, author
clarity, economy and Original-field checks remain fresh. Both ordinary delivery validators
run on the assembled complete result; any conflict with a carried record blocks delivery.
Original raw responses and the prior checked ledger remain immutable. Carryover is an
earlier judgment, never a new independent verification or a guarantee against old errors.

For repeated quotations, use the versioned exact text-reference syntax supplied in the
request. `$input_text` resolves only an assigned task's complete literal text; `$text`
resolves a literal string returned once in `texts`. Programs expand them before validation.
Use focused excerpts and separate independent components even when a whole-field reference
would be shorter. Shared wording does not imply shared judgments. These references remove
retyping, not evidence, qualifications or review tasks.

Before submission, local preparation validates actual source files and language-response
bindings. The packet runner collects common format, quote and unsupported-reuse problems
together after completed calls, retaining task IDs and distinguishing a format problem
from a new substantive judgment. Inspect the saved result list once, correct affected
records and dependencies, and run the ordinary gates. Do not rerun successful packets to
repair deterministic format issues, invent missing evidence, or automatically reclassify a
claim to make a validator pass. The result check is not semantic approval.

`efficiency.json` records carried versus fresh tasks; execution receipts record actual
phase wall time. Record development and repair intervals separately from ordinary
review. Report observed token usage and elapsed time, not projected savings.

## Complete evidence for each remaining task

Initial Reader, Expert, Advisor and Editor retain their full manuscript/image contracts; Advisor keeps complete assigned cards, and A retains the full manuscript. For targeted delivery work, include the complete source requirement, relevant final fields, report context, exact evidence and required cross-section prerequisites. Do not repeatedly submit all old reports, raw lanes, audit logs or unrelated cards. A path/hash/ID does not give an isolated reviewer access to its contents. Supply the content or inspected page actually needed. If relevance cannot safely be bounded, broaden the packet rather than truncate it.

## Combine related checks and keep records concise

Review a final passage's factual support, English/Chinese meaning, qualifications, author conditions and style together in the existing final-text pass. Do not add separate paid style, translation or correspondence passes for unchanged units. Preserve separate ledger fields and all independent requirements; combined tasks must not reveal B outputs to the source-only A reviewer or contaminate initial lanes.

Write concise dispositions with exact evidence and the decisive reason. Avoid repeating whole inputs inside explanations or returning private deliberation. Keep all required schema fields; do not omit conditions, alternatives or occurrence anchors. Compact JSON serialization may remove whitespace, not meaning. Post-freeze drafting receives verified findings, established drafting references and necessary unresolved coverage, without the entire resolved disposition history or the separate audit procedure.

## Batch to actual capacity

Group complete related packets using `audit_merge_obligations.py --max-batch-bytes` and verified text/image/output reserves. The byte bound is conservative, not an exact token count. Prefer shared-context batches over many tiny calls, while retaining complete source packets and output headroom. Oversized packets fail before submission; split independent tasks rather than cut evidence. Record every assigned ID and check unique complete returns. Do not maximize context occupancy or change the frozen Advisor coverage merely to reduce calls.

## Use bounded concurrency only for independent work

New `review_efficiency: 1` protocols use the [combined review workflow](review-workflow.md)
instead of the Advisor-only example below: after planning/case selection, schedule
Reader/Expert/Advisor/Editor together with three isolated requests by default.
Source-only execution/A shares one pass; B and final-text/language share one pass.
Existing gate criteria and A's hidden-later-output boundary remain unchanged.

Independent Advisor batches may be prefetched using `run_authorized_stage.py --prefetch-advisor --workers 2`. Prepare and pin requests/settings before concurrent submission; keep separate call directories and accept results through the ordinary sequential state transition. Dependent merge/verify, A/B and delivery-freeze steps stay sequential. Reduce concurrency when account limits or transport failures require it, without changing model/effort or enabling Fast. Concurrent calls reduce elapsed time, not aggregate tokens. The executor does not create additional review tasks or automatically retry failures.

## Require explicit settings authorization

Request `service_tier=default` explicitly. Fast/priority needs an explicit human instruction naming that tier and acknowledging its additional usage. A request to accelerate, hurry or meet a deadline is insufficient. Never infer this permission from keywords. Every reasoning-effort change, including a downgrade, needs an explicit human instruction naming the new effort. Keep the existing default unless the user chooses another; do not automatically tune effort, substitute models or enable Fast for performance.

The distributed transports require a local settings-authorization record with `authorized_by: "user"`, the exact `user_statement`, and exact `model`, `reasoning_effort`, `service_tier`. Fast/priority additionally requires `accepts_additional_usage: true`. The record documents an already explicit human authorization; an agent must not create it from an ambiguous request or self-authorize. A CLI option alone is not evidence of a human instruction. The validator checks structured exact settings; it does not classify prose, authenticate a human or make invented authorization legitimate. These private records must not be packaged in a release.

Example after the user explicitly chooses the settings:

```json
{
  "authorized_by": "user",
  "user_statement": "Use gpt-6-sol with xhigh reasoning and Standard service.",
  "model": "gpt-6-sol",
  "reasoning_effort": "xhigh",
  "service_tier": "default"
}
```

Pass `--settings-authorization AUTH.json` to the CLI stage runner. The optional Responses adapter takes the same record in `settings_authorization`. Existing live-call enable/disclosure requirements remain. Settings remain pinned within a frozen run; explicitly authorized changes use a new run/version, preserving previous artifacts. Record requested settings and actual returned service tier when available; a Fast request does not prove actual service or speed. Isolated transports may ignore host config, so enforce these settings in their invocation, not only in AGENTS.md.

## Prefer local validation and finish at the delivery gate

Run schema, unique-ID, exact-quote, source-hash, numbering and capacity checks locally. Try only deterministic, traceable formatting/anchor normalization; invented evidence or changed judgments need substantive review. Programs cannot certify evidence sufficiency, bilingual equivalence or natural prose. Inspect rendered PDF pages and retain the two required report-bound audits.

Failed or uncertain transport calls are not automatically resubmitted by the orchestration scripts. Inspect completed events and preserved output first; an uncertain attempt may already have consumed usage. Reconcile it before explicitly creating a separate attempt. Once necessary semantic checks, both delivery gates and requested layout checks pass, freeze and deliver. Do not launch another optional polishing pass or a new audit stage. Later requested changes renew only their affected records.

## Attempt timing and interpretation

Each isolated Codex attempt now writes END.json with UTC completion, elapsed wall
seconds and exit code; timed-out calls retain elapsed time in UNCERTAIN.json.
START.json and immutable raw output remain the attempt identity. Usage is taken
only from completed provider events. Sum per-call usage once, keep cached tokens
inside input, and do not treat missing failed-call usage as zero. END without a
validated audit is not a successful review. The run's wall-clock span and summed
call durations differ under concurrency. Local preparation, waiting and repair time
must be measured separately; never backfill these durations from token counts.


For new `delivery_reliability: 1` runs, apply [delivery reliability](delivery-reliability.md). Its explicit candidate/requirement decisions and local-validity recovery extend this contract; historical frozen runs retain the rules above. Local reuse does not imply whole-report approval, and style alignment does not imply improved quality.


For new `delivery_hardening: 1` runs, the additional [delivery hardening contract](delivery-hardening.md) governs source/component retention, actual-result barriers and scoped recovery. Older frozen protocols retain their existing rules.
