# dev.4：案例与导师行文知识怎样进入审阅

本版基于 dev.3，保留原 493 条 concern 和已发表论文案例快照。改动集中在学习事件、审阅应用和建议文本的来源链。没有把旧审阅标成 dev.4 新结果，也没有据此宣称已学会导师风格。

后续双库建设见 [Concern 与 Expression 学习及接入计划](concern-expression-plan.zh-CN.md)。截至2026-10-10，早期89包学习、双库接入、关联核对与局部三组开发比较已完成；补学四条遗漏长批注形成的238条快照原样保留。本轮完整学习已处置约定范围8,653处已确认导师批注，私有运行库更新为2,485条Expression，完整库Advisor的50批来源与条件验证已完成，完整四模块评测正在执行。选材不能只依赖Concern上下文，后续版本正文也须与导师实际措辞分开；详见[实际接入与范围](expression-integration-dev.4.md)。本文下述机制和初次验证保留其原始阶段范围；完整来源处置不等于导师偏好认证。

## 原来有什么，缺在哪里

原始内容审阅已经有 `closure_goal`；篇章审阅有 `organization_suggestions`，包括当前组织、拟议调整、理由、依赖和条件；Editor 可以直接给 `suggested_text`。所以报告中的“建议修改”并非全部在排版时凭空产生。但完整句段通常由诊断后的 proposal 阶段生成，不能把它称为原始审阅原文。

案例送给 Reader/Expert；导师 concern 送给独立 Advisor。dev.3 的案例使用记录主要是案例到检查对象的关联，concern 主要通过 check/card IDs 关联。它们能证明材料被提供、关联被记录，不能证明每段改写是怎样从材料学来的，也不能证明因果效果。

dev.3 的 proposal 准备器仅抽取 Reader 案例的任务、关系链和边界，没有沿最终意见恢复完整句子分工，也没有传递相关 concern 的完整六字段。原始发现、已复核要求和后续模型拟写三者容易在最终“建议文本”下混在一起。

另一方面，已有 Reader 清单并不短。继续增加“检查篇章、注意连贯”之类指令，仍不能回答具体段落为什么这样处理、导师曾改过什么、这个处理何时不适用。

## 本版实际接通的机制

1. **学历史修改事件。** 保留修改前、上下文、反馈、修改后和后续反馈，分别标注实际修改者、时间关系及缺失证据。提炼读者任务、改变的关系、具体动作、条件和例外；独立来源与同稿多版本分开。`editorial_learning.py` 准备冻结请求并校验候选记录，不自动调用模型或发布新知识。
2. **在本稿上检验学到的区别。** 新运行启用 `writing_transfer: 1`。Reader 逐一处理选中的案例；Advisor 在原 card disposition 上区分篇章作用、纯内容作用和不确定。应用记录指出原材料中的关系、本稿已有组织、适用条件、具体动作及其检查和输出。
3. **把篇章动作保留到最后。** 可选优化与必要修复都有独立出口；合并与复核继续按原稿证据裁定。追踪同时覆盖 finding 和 organization 的处置，包括将可选建议归入必要内容修复的情况。
4. **起草时恢复完整相关材料。** 传入相关 Reader 案例的完整运行视图和 concern 六字段。重复原始诊断留在本地审计文件，避免在提示词中反复附带；禁止恢复被排除的未验证写作配方。每项最终修改绑定实际报告摘录、目标原文支持和来源使用说明。没有材料支持的写法如实归于本稿分析。

新协议没有增加一个模型审阅通道，也没有放松 Reader/Advisor 隔离。技术正确性、缺失事实、可选行文改善仍分别判断。旧协议不被升级；旧输出只能生成注明“具体迁移未记录”的来源追踪。

## 怎样比“再清楚一些”更具体

例如 concern **C0340** 的条件性区别是：多种方法作为主要贡献时，摘要需要说明它们为什么并存、各自作用和条件，而非主要罗列实现步骤。其证据状态明确保留了没有后续干净摘要、最终压缩效果未核实的限制。这支持一次有条件的检查，不支持“导师一律喜欢某种摘要顺序”。

在新稿中，应进一步查明：两种方法究竟是互补、替代还是分条件使用？摘要哪些句子重复方法步骤？正文是否已经给出两种方法的代价与收益？据此保留哪句任务说明、压缩哪组步骤、在哪里补入方法关系、哪些结果和限定不能删。若事实齐备，交付协调后的摘要段落；关系仍未知，则明确待作者提供的信息。不能只写“缩短摘要、突出贡献”，也不能补造性能优势。

案例 **P01-C1** 则提供了另一种可观察组织：从开销目标、共享结构，到可利用性限制，再进入方法阶段。应学习这些句子的工作和依赖关系，检查新稿是否需要同样的解释连接；不能复制该论文的算法、数字或段落长度。这也不构成导师偏好的证据。

这两个示例是基于已有库记录的机制说明，未新增原始论文核查或行为实验。

## 验证与仍未证明的部分

本节保留初次实现的历史验证范围。后续经用户批准的实际来源学习与开发对照，使用独立的私有请求、输出、用量和处置记录；见[双库实际接入](expression-integration-dev.4.md)。后续进展没有将局部学习称为全库重学，也未将开发对照称为真实导师偏好评价。

本版用本地测试检查来源伪造、导师/学生混淆、同稿版本冒充独立证据、可选到必要修复的追踪、旧协议兼容及起草关联。另用已有完成运行做只读请求准备，检查真实材料能否走通新来源链。详细结果见 [验证记录](validation-v1.1.0-dev.4.json)。

这些检查不能证明“篇章意见更多、更细、更像导师”。该结论需要独立语义评估：以未用于提炼的来源家族检验实际行文问题覆盖、具体性、误报、事实保留和可采用改写，冻结输出后再读导师反馈。评估案例影响时保持通用审阅规则及模型设置相同；dev.3 与 dev.4 的整体比较另行归因。初次机制实现没有新的外部模型调用；后续授权的真实调用另行记录，没有把局部学习称为全库重学。
